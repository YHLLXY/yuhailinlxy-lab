# OG 分享卡调研（2026-10-17）

> **触发**：v0.1 上线后，把 https://lab.yuhailinlxy.com 发给别人，预览只有标题和描述，没有图。
> **结论先行**：做一张 **1200×630 PNG、小于 300 KB、站点级共用** 的静态分享卡；用本地 HTML 模板 + 系统 Edge 渲染，产物提交进 `public/og.png`，不引入任何新的构建依赖。

---

## 1. 规格：为什么是 1200×630

| 平台 | 推荐尺寸 | 体积上限 | 缓存 | 备注 |
|---|---|---|---|---|
| Facebook | 1200×630（1.91:1） | 8 MB | 未查到一手值 | 1.91:1 的源头 |
| X | 1200×675（16:9） | 5 MB / 4096×4096 | 未查到 | 给 1200×630 也能用，会裁掉少量边缘 |
| LinkedIn | 1200×627（1.91:1） | 5 MB | 7 天 | 改图后用 Post Inspector 强制重抓 |
| Slack | 1200×630 | 5 MB | 24 小时 | |
| Discord | 1280×640（2:1），也收 1200×630 | 8 MB | 未查到 | **缺 `twitter:card` 只给 80×80 缩略图** |
| WhatsApp | 1200×630 | 软上限约 300 KB | 未查到 | 超过可能被降级或不显示 |
| Telegram | 1200×630 | 5 MB | 未查到 | 会先读 `og:image:width/height` 占位 |

**取舍**：

- 主尺寸取 **1200×630**。它是 Facebook 定义、其余平台跟随的默认值；X 偏 16:9，但 1.91:1 只损失边缘。
- **目标体积 < 300 KB**。这是 WhatsApp 的软上限，也顺便让任何平台都不会因为体积降级。
- **关键内容放在中心 66%**。X 会裁边、iMessage 锁屏会方裁、Slack 移动端可能方裁；文字距边 ≥ 80 px，标题不贴边。

> 这张表是**平台口径汇总**，不是 OGP 规范——[ogp.me](https://ogp.me/) 本身不规定尺寸。
> 表格数字来自 [env.dev 2026 对照表](https://env.dev/guides/opengraph-image-sizes)，属于二手汇总；Facebook 的 8 MB 未追到一手文档。见第 7 节。

## 2. 要写的标签

```html
<meta property="og:type" content="website" />
<meta property="og:site_name" content="动效实验室" />
<meta property="og:title" content="动效实验室" />
<meta property="og:description" content="…" />
<meta property="og:url" content="https://lab.yuhailinlxy.com/" />
<meta property="og:locale" content="zh_CN" />

<meta property="og:image" content="https://lab.yuhailinlxy.com/og.png" />
<meta property="og:image:type" content="image/png" />
<meta property="og:image:width" content="1200" />
<meta property="og:image:height" content="630" />
<meta property="og:image:alt" content="…" />

<meta name="twitter:card" content="summary_large_image" />
<meta name="twitter:image" content="https://lab.yuhailinlxy.com/og.png" />
<meta name="twitter:image:alt" content="…" />
```

要点：

1. **必须是绝对 URL**。相对路径抓取器解析不了，直接退回纯文字卡。
2. **`og:image:alt` 是 OGP 规范里的属性**（[ogp.me](https://ogp.me/) 示例中有 `og:image:alt`），不是 Twitter 私有扩展；两边都写。
3. **`twitter:card` 不是可选项**。Discord 只看它决定大图还是 80×80 缩略图；og 的 width/height 只是辅助。
4. **宽高必须和文件真实尺寸一致**。写错会让部分平台按错误比例预留版面，图加载后跳一下。
5. **换图不要覆盖同名文件**。LinkedIn 缓存 7 天、Slack 24 小时，抓取器只认 URL；要换就换文件名（`og-2026-11.png`）或加版本参数。

## 3. 方案盘点：为什么不引 satori

| 方案 | 成熟度 | 成本 | 判断 |
|---|---|---|---|
| A. Figma / PS 手绘一张 | 高 | 改文案要重画，不可复现 | 否 |
| B. 构建期 satori + resvg（`astro-og-canvas` 同路线） | 高，Vercel / Next.js 同源 | 需 CJK 字体文件、CSS 子集、2 个新依赖 | 否 |
| C. 运行时 `@vercel/og` | 高 | 需要 serverless 函数 | 否——本站是纯静态 |
| D. 本地 HTML + 系统 Edge 截图 | 中 | 复用已有 `playwright-core`，零新依赖 | **选它** |

**B 的问题不是不能用，是不值得**：satori 的价值在「页面多、内容动态」——每篇文章一张卡。本站只有一张站点级图，文案一年改不了几次；为它引入 CJK 字体子集（动辄几 MB）+ resvg 原生模块，维护面积比收益大。

**D 的代价**：生成依赖本机 Edge 与系统中文字体，换机器不一定 1:1 复现。缓解：脚本进仓库、模板与数据全部在仓库里、产物本身也进仓库——**即使脚本跑不起来，图还在**。

> 参考实现：[Build-Time OG Images with Satori and Astro](https://dev.to/morellodev/generating-og-images-at-build-time-with-satori-and-astro-4b4b)（同结论：静态站应在构建期出图，而不是每次请求渲染）。

## 5. 设计与生成

- 复用站点 token：底 `#f6f4f1`、纸面 `#ffffff`、墨 `#282728`、次要 `#666d7a`、曲线蓝 `#006cac`、曲线橙 `#c2410c`。
- 左文右图：左边是首页原句「动效不是装饰，是一个决策。」，右边是首页同款 **out-expo / in-expo 同帧对照**——分享卡和落地页说同一件事。
- 曲线控制点**从 `easings.ts` 读**，不手抄；数据改了图会跟着变，改不动脚本会报错，而不是悄悄画错。
- 输出 1200×630 @1x。1x 的文字在分享卡的实际展示尺寸（约 500–600 px 宽）下已经足够；2x 只会让文件大三倍。
- 生成命令：`node scripts/og.mjs`（从真实终端跑，原因见 `scripts/shoot.mjs` 顶部注释）。

## 6. 验证口径

1. PNG 文件头 IHDR = 1200×630，体积 < 300 KB；
2. `dist` 里每个 HTML 都有绝对 URL 的 `og:image`，且指向真实存在的文件；
3. `twitter:card=summary_large_image`、`og:image:alt` 非空；
4. 线上 `/og.png` 返回 200 与 `image/png`；
5. **人眼看图**：缩到 600 px 宽仍能读清标题（分享卡的真实显示尺寸）。

第 5 条不能省——尺寸对、标签对，但字太小或被裁掉，等于没做。
